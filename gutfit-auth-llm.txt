

---

This is a critical decision point. The choice between an Easypanel-based deployment and a full IaC (Infrastructure as Code) strategy on Proxmox will define the scalability, resilience, and autonomy of your entire platform.

**Executive Recommendation:**

For a "super solid, better-than-best-of-practices" system that embodies the "Co-Evolution Engine" philosophy, the **Proxmox API + VSCode + custom Control Plane (proxmoxMCP) is the superior, long-term strategy.**

While Easypanel is excellent for rapid deployment on a single server, it creates a fragile "pets" architecture that is difficult to scale, replicate, and recover. The Proxmox/IaC approach creates a robust "cattle" architecture where every component is disposable, replaceable, and defined entirely in code. This is the only way to achieve true autonomous configuration.

Here is the comprehensive deployment strategy built on this principle.

## The Autonomous Deployment Strategy: A Phased IaC Approach

We will build a system that can provision and configure your entire Gutfit ecosystem from a single command.

### Phase 1: The Foundational Blueprint with Terraform

**Goal:** Define the entire virtual infrastructure—VMs, networks, storage—in declarative code.

**Tools:**
*   **Terraform:** To provision resources in Proxmox via its API.
*   **Proxmox Provider:** The Terraform plugin that talks to your Proxmox server.

**Your Project Structure:**
```
/gutfit-infrastructure
├── main.tf                 // Main Terraform configuration
├── variables.tf            // Input variables (e.g., VM sizes)
├── terraform.tfvars        // Your specific values
├── modules/
│   ├── vm/                 // Reusable module for creating a VM
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── templates/
│   │       └── user-data.yaml // Cloud-Init config
│   └── database/           // Module for a dedicated DB VM
└── environments/
    ├── staging.tfvars
    └── production.tfvars
```

**Example `main.tf`:**
```hcl
terraform {
  required_providers {
    proxmox = {
      source  = "telmate/proxmox"
      version = "2.9.14"
    }
  }
}

provider "proxmox" {
  pm_api_url = var.proxmox_api_url
  pm_api_token_id = var.proxmox_api_token_id
  pm_api_token_secret = var.proxmox_api_token_secret
}

# Create the main application server VM
module "gutfit_app_server" {
  source = "./modules/vm"

  vm_name = "gutfit-app-01"
  vm_id   = 101
  target_node = "pve" // Your Proxmox node name
  clone = "ubuntu-2204-template" // A pre-created cloud-image template
  user_data_file = "${path.module}/modules/vm/templates/user-data-app.yaml"
}

# Create a dedicated database server VM
module "gutfit_db_server" {
  source = "./modules/vm"

  vm_name = "gutfit-db-01"
  vm_id   = 102
  target_node = "pve"
  clone = "ubuntu-2204-template"
  user_data_file = "${path.module}/modules/vm/templates/user-data-db.yaml"
}
```

### Phase 2: Zero-Touch Configuration with Cloud-Init & Ansible

**Goal:** Automatically install and configure all software inside the newly created VMs.

**Tools:**
*   **Cloud-Init:** Built into the Ubuntu cloud image. Runs a script on first boot to do basic setup (install Docker, set hostname, etc.).
*   **Ansible:** The workhorse for configuration management. It will install and configure Authentik, Nextcloud, Moodle, and your services with precision.

**Example `user-data-app.yaml` (Cloud-Init):**
```yaml
#cloud-config
package_update: true
packages:
  - docker.io
  - docker-compose
  - python3
  - python3-pip

runcmd:
  - pip3 install ansible
  - echo "ansible_user ALL=(ALL) NOPASSWD:ALL" >> /etc/sudoers
  # Clone your configuration repository
  - git clone https://github.com/your-org/gutfit-ansible-playbooks.git /opt/gutfit
  # Run the Ansible playbook for this server
  - ansible-playbook /opt/gutfit/playbooks/app-server.yml
```

**Example `app-server.yml` (Ansible Playbook):**
```yaml
---
- hosts: localhost
  become: yes
  vars:
    # Load credentials from an encrypted vault file
    authentik_secret: "{{ vault_authentik_secret }}"
    nextcloud_admin_pass: "{{ vault_nextcloud_pass }}"

  tasks:
    - name: Create Authentik Docker network
      docker_network:
        name: gutfit-net

    - name: Deploy Authentik
      docker_compose:
        project_name: authentik
        definition:
          version: '3.8'
          services:
            server:
              image: ghcr.io/goauthentik/server:latest
              # ... full authentik docker-compose config here
              environment:
                AUTHENTIK_SECRET_KEY: "{{ authentik_secret }}"
                # ... other variables
            # ... worker, postgres, redis services

    - name: Deploy Nextcloud
      docker_compose:
        project_name: nextcloud
        definition:
          # ... full nextcloud docker-compose config
          # It will be configured to point to the Authentik URL

    - name: Deploy Moodle
      docker_compose:
        project_name: moodle
        definition:
          # ... full moodle docker-compose config
```

### Phase 3: The "Gutfit Control Plane" (Your `proxmoxMCP`)

**Goal:** Create a custom orchestration layer that can manage the lifecycle of your platform.

This is where your creative invention comes to life. The "proxmoxMCP" is not an off-the-shelf product; it's a custom API service you build.

**Technology:** A Node.js/Express or Python/FastAPI application.

**Features of the `proxmoxMCP` API:**

*   `POST /deploy-environment`:
    *   Accepts a payload like `{ "environment": "staging", "version": "v1.2.3" }`.
    *   It runs `terraform apply -var-file=environments/staging.tfvars`.
    *   It waits for Terraform to finish, then triggers the Ansible playbooks.
    *   It returns the status and IP addresses of the new environment.

*   `POST /scale-service`:
    *   Accepts `{ "service": "app", "instances": 3 }`.
    *   It uses the Terraform Proxmox provider to launch 2 more identical VMs from the `app-server` module.
    *   It automatically registers them with a load balancer.

*   `GET /health`:
    *   Queries the health of all services (Authentik, Nextcloud, DB, etc.) across all VMs.
    *   Returns a complete status dashboard.

*   `POST /self-heal`:
    *   Triggered by an alert (e.g., "Nextcloud is down").
    *   It can attempt to restart the Docker container, or if that fails, destroy the VM and redeploy it from the Terraform blueprint.

**The VSCode Extension:**
You could create a simple VSCode extension that provides a GUI for your `proxmoxMCP` API. A "Gutfit Deploy" button in your IDE that calls the `/deploy-environment` endpoint. This creates a seamless, developer-centric workflow.

## The "Package" for Deployment

The final "package" is your Git repository containing:
1.  The `terraform/` directory with all your `.tf` files.
2.  The `ansible-playbooks/` directory with all your `.yml` files and an encrypted `vault.yml` for secrets.
3.  The source code for your `gutfit-mcp-api/` service.
4.  A `Makefile` for simple commands:
    ```makefile
    deploy-staging:
    	cd terraform && terraform apply -var-file=environments/staging.tfvars

    destroy-staging:
    	cd terraform && terraform destroy -var-file=environments/staging.tfvars
    ```

To deploy your entire platform, you or a CI/CD pipeline would simply run `make deploy-staging`.

## The Easypanel "Quick Start" Alternative (For Comparison)

If you needed to get something running *today* on your existing Easypanel server, you could use a "heavy script" approach. This is **not recommended for production** but serves as a good comparison.

**The `easypanel-setup.sh` script:**
```bash
#!/bin/bash

# This script is a fragile alternative to the IaC approach.
# It assumes root SSH and app credentials are available.

# 1. Install Docker Compose projects via Easypanel API
# (Pseudo-code, as the exact API calls would vary)
curl -X POST "https://easypanel.gutfit.co/api/projects" \
  -H "Authorization: Bearer $EASYPANEL_API_TOKEN" \
  -d '{"name": "authentik", "docker_compose_yaml": "..."}'

# 2. Configure Authentik via its API
# Wait for Authentik to be healthy, then...
AUTHENTIK_TOKEN=$(curl -X POST "https://auth.gutfit.co/application/o/token/" -d "...")
curl -X POST "https://auth.gutfit.co/api/v3/core/applications/" \
  -H "Authorization: Bearer $AUTHENTIK_TOKEN" \
  -d '{"name": "Nextcloud", ... }'

# 3. Configure Nextcloud via its `occ` command
ssh root@app_server "docker exec -it nextcloud php occ config:system:set ..."
```

**Why this is inferior:**
*   **Imperative, not Declarative:** It's a series of steps, not a definition of a desired state. If it fails halfway through, your state is unknown.
*   **Not Idempotent:** Running the script twice will likely cause errors.
*   **Hard to Version Control:** Changes are spread across API calls and SSH commands.
*   **Doesn't Scale:** This only works for a single server. It cannot create new VMs or manage a multi-server infrastructure.

By choosing the Proxmox/IaC path, you are investing in a system that is as robust, scalable, and autonomous as the "Co-Evolution Engine" it is designed to support.
